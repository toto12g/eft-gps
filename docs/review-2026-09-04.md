## A. データを最新にする

同梱データは 2026-09-04 04:51 の生成なので、中身自体はすでに最新。ここに書くのは
「次に更新するときに踏む穴」で、いま `data/calib-overrides.json` が空（＝手動校正がゼロ）の
**今が、いちばん安全に回せるタイミング**。

1. 更新前に `git status` を clean にする。`data/` は全書き換えなので、他の変更と混ざると差分が読めなくなる。
2. `py tools/build_data.py --refresh`（約 30 MB 取得。鍵名が変わらない更新なら `--no-keys` で 16 MB 節約）
3. `py tools/run_tests.py` で 102 件を確認。校正まわりのテストが upstream の SVG 変更を検知する。
4. `py tools/shoot_calib.py` で 10 枚を目視。脱出口が図の出口に乗っているかだけ見れば十分。
5. mapdb の要約を前後で比べる（マップ数・`poiTotal`・`taskCount`）。減っていたら上流の欠測を疑う。

### A-1 【高】新しいマップ／夜バリアントが増えると、マップ判定が無言で壊れる

座標系を共有するシーン（`night-factory`、`the-lab-dark`、`ground-zero-21`）は
`tools/build_data.py:64` の `SCENE_ALIASES` に**手で**書いてある。上流に新しい夜／イベント版が
増えたときに追記を忘れると、その 2 マップは互いの POI が距離 0 になり、判定の要である
「2 位 / 1 位」の比が常に 1.0 に張り付いて機能しなくなる。
いまのテストは `night-factory` と `ground-zero` を名指しで見ているだけなので、新顔は素通りする。

**直し方**: ビルドの最後に「全マップ対の相互最近傍」を計算し、**相手の POI の 90 % 以上が 1 m 以内にある対**を
エラーとして落とす。エイリアスの書き忘れがその場で分かる。

### A-2 【中】`--refresh` は `maps/*.svg` も上書きする

`fetch_svg()` は `refresh` が真なら既存の SVG を再取得して上書きする。解析的校正は毎回 viewBox を
読み直すので今は問題ないが、**手動校正（`calib-overrides.json`）を入れた後は、その affine が
古い viewBox に固定される**ため、上流が SVG を差し替えた瞬間にそのマップだけズレる。

**直し方**: override に `svgViewBox` だけでなく SVG のハッシュも記録し、取得した SVG と食い違ったら
ビルドを警告で止める。**手動校正を入れるより先に、いまデータ更新を回しておく**のが最も安い。

### A-3 【中】`mapdb.json` の `version` が 1 のまま、アプリ側も見ていない

スキーマが変わっても version は 1 のままで、`loadMapDb()` は照合していない。いまはその場しのぎとして、
UI 側で `m.taskFile === undefined` を見て「データが古いようです。Ctrl+Shift+R で再読み込みしてください」と
出している（`src/app/main.js:212` 付近）。原因の説明としては弱い。

**直し方**: `version` を上げる運用にして、`loadMapDb()` で期待値と比較し、違えば
「データとコードの版が違う」と明示的に投げる。Service Worker のキャッシュ削除も同時に促す。

### A-4 【低】座標が ±3276.7 m を超えると、無言で切り詰められる

`poi.bin` は Int16 デシメートル。`tools/build_data.py:636` の `quantize()` が
`max(-32768, min(32767, …))` で clamp する。現状の最大は Lighthouse の 1051.8 m で余裕は 3 倍あるが、
超えた点は**マップの端に貼り付いた偽の POI** になり、最近傍距離を静かに壊す。

**直し方**: clamp が 1 件でも発生したらビルドで警告を出す（5 行で済む）。

### A-5 【低】翻訳が新規テキストに追いつかないと、静かに英語へ落ちる

`apply_translations()` は 日本語 → 英語 → 元キー の順に当てる。壊れはしないが、パッチ直後は
新タスク名だけ英語という状態になる。今のテストはマップ名と脱出口名しか見ていない。

**直し方**: 「タスク名の 9 割以上が非 ASCII を含む」程度の緩いテストを 1 本足す。

## B. もう配っているのに、使っていないデータ

ここが今いちばん費用対効果が高い領域。**取得も配信も済んでいて、読み手のコードだけが無い**もの。
データを増やさずに機能が増える。

### B-1 【未使用】マップ非依存タスク 167 件が、どこにも出ていない

`data/tasks/_any.json`（92 KB / 167 タスク）と `mapdb.json` の `anyTaskFile` / `anyTaskCount` は
生成・配信されているが、`src/` 全体で一度も参照されていない。「スカブを 10 体倒す」型の、
どのマップでも進むタスクが丸ごと見えない。全 517 タスクのうち **3 分の 1 弱**がこれに当たる。

**直し方**: `loadTasks()` でマップ別ファイルと `_any` を結合し、一覧では「どのマップでも」と
印を付けて末尾にまとめる。目標地点が無いので地図描画は不要、一覧だけ。

### B-2 【未使用】フロアの自動切替に必要な情報が、全部すでに入っている

`mapdb.maps[].tarkovDev.layers[]` に、階ごとの **表示名**（"2nd Floor" / "Underground" / "Bunkers"）、
**高さ範囲**、**適用される平面矩形**（"dorms", "big red 2nd" などの名札つき）が入っている。
Customs だけで 4 レイヤ・20 近い矩形。にもかかわらず現在のフロア選択は手動プルダウンで、しかも
表示名は SVG のグループ ID をそのまま `_` → 空白に置換したもの（`src/app/main.js:705`）。

実害は見た目だけではない。地下や寮 3 階にいるとき、**別の階の図の上に自分のマーカーが乗る**ので、
いちばん位置を知りたい状況でいちばん読めない図になる。

**直し方**: サンプルの `y` と `(x,z)` を `extents` に照合してフロアを自動選択し、プルダウンの表示名も
`layers[].name` に差し替える。手動選択は「固定」トグルとして残す。

### B-3 【未使用】「スイッチを入れないと使えない脱出口」が見分けられない

API の extract は `switch` / `switches` を持っている（例: Customs の ZB013）。`build_data.py` は
`name / key / faction / position / outline` しか写していないので、**要スイッチの脱出口が、
無条件の脱出口と同じ見た目**で並ぶ。最寄り脱出口の案内としては危険。

**直し方**: `switches` を mapdb に写し、該当の脱出口に印を付ける。既にある「スイッチ」レイヤの地点と
ID で結べば、タスクの鍵 → 扉と同じ導線（`taskKeyDoors`）がそのまま流用できる。

### B-4 【未使用】湧き位置と砲撃ゾーンがレイヤになっていない

`spawns`（Customs だけで 278 点。`sides` と `categories` つき）は最近傍計算用の POI としてだけ使われ、
地図には出ない。`artillery`（砲撃）は 8 マップにあるのに、そもそも取得していない。
「危険地帯」レイヤに地雷原と狙撃ゾーンはあるのに砲撃だけ無いのは、使う側から見ると穴に見える。

**直し方**: `POI_COLLECTIONS` に `artillery` を足し、landmarks に `spawn` / `artillery` の 2 種を追加。
湧き位置は数が多いのでボスと同じ 20 m 格子の間引きを流用する。

### B-5 【低】拾っているのに出力していない値が 2 つある（死にコード）

`tools/build_data.py:699-700` で `raidDuration` と `coordinateToCardinalRotation` を `merged` に
入れているが、最終的な `entry` に含めていないので `mapdb.json` には出ない。後者は
「ワールド座標の +Z が真北から何度ずれているか」で、**地図に方位ローズを出すために必要な唯一の値**。

**直し方**: 2 行を `entry` に追加。使わないなら 2 行を消す。どちらかにする。

### B-6 【低】クエストアイテム・地名の回転／サイズも書き出し済みで未使用

目標の `qi`（クエストアイテム名）と `itMore`（8 件で打ち切った残数）、地名ラベルの `r`（回転）と
`s`（サイズ）は、データにあるのに UI が読まない。`qi` は「持ち物」の説明として素直に効く。

## C. バグと壊れやすい所

上 3 件はレイド中に実際に踏む。

### C-1 【高】localStorage が 1 文字壊れると、アプリが真っ白になる

`src/app/main.js:47` と `:56` の `JSON.parse` は**モジュール評価中**に走る。`boot().catch()` の
エラー表示はまだ登録されていないので、例外は誰にも捕まらず、画面には何も出ない。
ユーザーから見ると「開いたら真っ黒で何も起きない」で、原因にたどり着く手がかりがゼロ。

**直し方**: `safeParse(key, fallback)` を 1 つ作って両方をくるむ。壊れていた項目は捨てて既定値に戻し、
起動後にサイドバーへ「保存された設定を復元できなかったので初期値に戻しました」と 1 行出す。

### C-2 【高】レイド外のスクリーンショットが、累積判定を汚染したまま消えない

`src/app/main.js:636` は `validateSample()` の**前**に `tracker.add()` している。つまりハイドアウトや
メニューで撮った 1 枚も、`NOT_IN_RAID` と判定された後も累積に残り続ける。

効き方が二重で悪い。`MapTracker.rank()` の bbox 足切り（`src/verify/index.js:162`）は
`entries.every(...)` で**全サンプルが収まるマップだけ**を候補にするので、原点付近の 1 枚が混ざると
正解マップが候補から丸ごと消える。残るのは「1 つも残らなければ足切りしない」という保険だけで、
これは静かに精度を落とす形の失敗。

**直し方**: 判定を先に行い、`NOT_IN_RAID` なら `tracker` に入れない（または入れた 1 件を取り消す）。
あわせて bbox 足切りを `every` から**「95 % のサンプルが収まる」**に緩め、外れ 1 枚で候補が消えないようにする。

### C-3 【高】`applySample()` が非同期なのに、誰も待っていない

`applySample()` は中で `await selectMap()`（SVG 取得・レイヤ全消し・タスク再読込）を行うが、
呼び出し側の `handleScreenshot()` は待たない。とくに `src/app/main.js:572` の「直近 20 枚を読み込む」は
**20 本を同時に走らせる**。マップ自動切替が絡むと、レイヤ掃除と描画が交錯してマーカーが消える・
軌跡が途切れる、が起こり得る。

**直し方**: 1 本のプロミス連鎖（`queue = queue.then(() => applySample(...))`）で直列化する。
監視側も同じキューに載せれば、連写しても順番が保たれる。

### C-4 【中】最寄り脱出口が、陣営フィルタを無視してスカブ用を常に捨てている

`src/app/main.js:814` が `if (e.faction === 'scav') continue;` と決め打ちしている。サイドバーの
「脱出口の表示」チップで PMC を外していても関係なく、**スカブランでは案内される脱出口が丸ごと嘘**になる。
地図上の描画だけがチップに従っていて、文字の案内だけが従っていない、という食い違い。

**直し方**: `nearestExit()` に `state.factions` を渡し、描画と同じ集合で絞る。

### C-5 【中】マップが自動で切り替わると、選んでいたタスクが黙って消える

`selectMap()` → `loadMapTasks()` の先頭で `state.activeTask = null`（`src/app/main.js:212`）。
トランジットで移動したときにも走るので、追いかけていた目標地点が理由の説明なく消える。

**直し方**: 切替後のマップに同じタスク ID があれば選択を引き継ぐ。無ければ
「このタスクは ◯◯ の目標です」と 1 行残す。

### C-6 【中】タスク／地点データの読み込み失敗が、リロードするまで永久に残る

`src/app/tasks.js` と `landmarks.js` は**失敗もキャッシュ**する（`cache.set(mapKey, failed)`）。
一瞬の通信断でも、そのマップは以後ずっと「タスクデータを読めませんでした」のまま。
`clearTaskCache()` は用意されているのに UI から呼べない。

**直し方**: 失敗はキャッシュしない。もしくはエラー表示に「再試行」ボタンを付けて `clearTaskCache()` を叩く。

### C-7 【中】新着スクリーンショットが、入力欄に書きかけの文字を上書きする

`handleScreenshot()` が `$('input-text').value = filename` を無条件に行う。監視中に座標を
手入力していると、次の 1 枚で消える。

**直し方**: 入力欄が空、またはフォーカスされていないときだけ上書きする。

### C-8 【低】SVG だけキャッシュ制御が抜けている

`mapdb.json` / タスク / 地点は `cache:'no-cache'` を付けているのに、`src/app/map.js` の
`fetch('./' + mapData.svg)` は素のまま。GitHub Pages の `max-age=600` により、
**デプロイ直後の 10 分間、古い SVG と新しい affine** が組み合わさり得る。ちょうど
「更新したのにズレている」という原因の分かりにくい報告になる。

**直し方**: 同じ `cache:'no-cache'` を付ける。`src/*.js` も同様。

### C-9 【低】毎秒フォルダを全列挙している

`ScreenshotWatcher.poll()` は 1 秒ごとに `dirHandle.keys()` を回す。名前だけを返す最も安い呼び出しでは
あるが、スクリーンショットを消さない人のフォルダは数千件まで育つ。差分方式の設計判断自体は正しいので、
間隔だけの問題。

**直し方**: 件数に応じて間隔を伸ばす（例: 1000 件超で 2 秒）。あるいは新着が続く間だけ 1 秒に上げる。

### C-10 【低】選択中のタスクとフロアだけ、リロードで消える

マップ・ピン・レイヤ・陣営・自動切替は localStorage に保存されているのに、タスク選択とフロア選択だけ
保存されない。権限の取り直しでリロードが必要な設計なので、地味に効く。

## D. マップ判定の弱点

「単発では決めない・窓では切らない・レイド累積で決める」という結論はデータに裏打ちされていて、
設計としては妥当。以下は、その前提が崩れる場所。

### D-1 【中】Icebreaker はハイドアウトと座標がほぼ重なっている

Icebreaker の bbox は `x[-11.7, 11.6] / z[-75.2, 48.8]`、POI はわずか 53 点。原点付近。
README にも「ハイドアウトの 1 位は icebreaker 4.72 m」と記録されている。いまは
「2 位 / 1 位 < 2 ならレイド外」で救っているが、**本当に Icebreaker に行ったときも同じ形で誤判定される**
可能性があり、そこは未検証。

**直し方**: Icebreaker のレイドを 1 回撮って回帰データに足す。救えないなら、ハイドアウトの座標帯
（原点付近かつ `y` が特定範囲）を明示的な除外規則にする。

### D-2 【中】トランジット追随の閾値だけ、実測の裏付けが無い

`switchWindow = 4` / `switchRatio = 6`（`src/verify/index.js`）は、他の閾値と違って実データから
決まっていない。累積を捨てる操作は**いちばん壊れると痛い経路**なので、ここだけ勘なのは釣り合いが悪い。

**直し方**: Customs → Streets のトランジットを 1 往復撮って、テストの回帰データに加える。

### D-3 【低】レイドの終わりを検出していない

忘れる条件は「10 分の空白」だけ。撮影間隔が空きやすい遊び方だと同一レイド中にリセットされ、
逆に連続してレイドに入ると前のレイドを引きずる。

**直し方**: 脱出口の 20 m 以内に入った、またはゲーム内時計が不連続に飛んだら
「レイド終了の可能性」として区切る。

### D-4 【低】「マップが違う」と言われた根拠が、数字でしか出ない

いま出るのは `最寄りマップ woods 5.40 m（2 位 …, 比 1.3）` という数値だけ。判定が疑わしいときに、
ユーザーが確かめる手段がない。

**直し方**: 最寄り POI を候補マップ上に 1 点描く。「そこに何も無い」ことが目で分かれば十分。

## E. 使っていて困る所

### E-1 【高】The Lab に地図が無い。ただし、出すための材料はもう揃っている

地図画像が無いのは `the-lab` / `icebreaker` / `the-labyrinth` の 3 つ。このうち
**The Lab だけは今日中に出せる**。`maps/Labs.svg` は既にリポジトリにあり（縦横比が上流の `bounds` と
10 % 合わないため自動採用を見送っただけ）、校正の参照点になる脱出口が 7 箇所そろっている。
`calibrate.html` で 3〜4 点打てば済む。

The Lab は POI 980 点・タスク 24 件・地点 140 件を持っていて、**データだけあって地図が無い**という
一番もったいない状態。Icebreaker と Labyrinth は上流に SVG 素材そのものが無いので、これとは別問題。

**直し方**: `calibrate.html` で `Labs.svg` に脱出口を対応づけ → `data/calib-overrides.json` に貼る →
`py tools/build_data.py`。Labs.svg は `Technical_Level` / `First_Level` / `Second_Level` の 3 層構造なので、
校正は 1 層に固定して行うこと。

### E-2 【中】表示されている位置が「いつのものか」分からない

現在地はスクリーンショットを撮った瞬間で止まるが、画面上のマーカーは 1 秒前でも 5 分前でも同じ見た目。
撮り忘れたまま移動しているときに、**古い点を現在地だと信じて動く**のがこのツールで最も危ない誤り。

**直し方**: 「12 秒前」を常時表示し、経過に応じてマーカーの不透明度を落とす（30 秒で 0.5、2 分で 0.25 など）。
撮影を促す表示はここに置くのが自然。

### E-3 【中】北がどこか分からない

矢印は自分の向きを示すが、基準になる方位が図に無いので「方位 77°」と言われても地図と結び付かない。
必要な値（`coordinateToCardinalRotation`）は上流から取得済みで、出力し忘れているだけ（B-5）。

**直し方**: 方位ローズを右下に固定表示。アフィンに写した +Z 方向を描けば、回転・反転したマップでも正しく向く。

### E-4 【中】タスクの検索が日本語名でしかできない

タスク名も目標説明も日本語だけをデータに持っている。読みやすさの判断としては正しいが、
**攻略情報は英語名で流通している**ので、Wiki や配信で見た名前では引けない。

**直し方**: 検索用に英語名だけを `ne` のような短いキーで併記する（表示は日本語のまま）。
`build_data.py` は既に `tasks_en` を取得済みなので追加取得は不要。

### E-5 【低】レイドの記録が残らない

軌跡は 60 点で古いものから消え、保存も書き出しもできない。「さっきどこで撃たれたか」を後から見る
用途に応えられていない。

**直し方**: レイド単位で軌跡を localStorage に保存し、JSON 書き出しを 1 ボタン付ける。

### E-6 【低】サイドバーが 340 px 固定で、畳めない

第 2 モニタが小さい・縦置きだと地図の面積が足りない。PWA の単独ウィンドウで使う想定なら、
地図を最大化できることの価値は大きい。

**直し方**: サイドバーの折りたたみトグル（Tab など）と、幅のドラッグ変更。

### E-7 【低】PMC / スカブ / 共通が色だけで区別されている

脱出口の陣営は緑・橙・黄の色分けのみ。暗い地図の上の小さな点で、色覚特性によっては判別できない。

**直し方**: 形も変える（丸／三角／四角）。既に landmarks 側は形で区別しているので、揃えるだけ。

### E-8 【低】タスクの進行管理が無い

全 517 件から毎回探すことになる。完了済みを隠す、Kappa 必須だけ、トレーダー別、といった絞り込みは
ローカル保存だけで実現できる。

### E-9 【低】2 点間の距離を測る手段が無い

現在地からの距離は出るが、「あの建物からあの橋まで」は測れない。ものさしモードが 30 行程度で入る。

## F. 配布と更新

### F-1 【中】Service Worker のキャッシュ版が手動更新

`sw.js:16` の `VERSION = 'eft-gps-v5'` を、データやコードを更新するたびに手で上げる運用。
上げ忘れると、インストール時にプリキャッシュした古い一式が残る。「ネットワーク優先・キャッシュ退避」なので
致命傷にはならないが、オフライン時だけ古い版という追いにくい状態を作る。

**直し方**: `build_data.py` の最後に `sw.js` の `VERSION` をビルド時刻で書き換える。

### F-2 【中】プリキャッシュに、地図の SVG とアプリの半分のモジュールが入っていない

`PRECACHE` は 19 件で、`src/app/tasks.js` / `landmarks.js` / `pins.js` / `calibrate.js` と
`maps/*.svg` が抜けている。インストール直後にオフラインへ行くと**地図が 1 枚も出ない**。
タスクと地点のファイルは `install` 時に mapdb から拾って追加しているので、同じ場所に SVG を足すだけで済む。

テスト T13 は「列挙されたものが実在するか」しか見ないので、**抜けは検知できない**。

**直し方**: `install` で `db.maps[].svg` も `cache.add`。テスト側は「`index.html` から辿れる
ES モジュールが全部 PRECACHE にあるか」を見る形に変える。

### F-3 【低】更新が入ったことをユーザーに伝えていない

`skipWaiting()` + `clients.claim()` で新しい Service Worker が即座に交代する。ネットワーク優先なので
実害は小さいものの、開いたままのタブでは古い JS と新しいデータが同居し得る。

**直し方**: `controllerchange` で「新しい版があります／再読み込み」を 1 行出す。

## G. ビルドとテスト

### G-1 【中】テストが 1 回だけ 2 件落ちた（同じコードで再実行すると全部通る）

今回の確認で、初回は `pass=100 fail=2`、以後 4 回連続で `pass=102 fail=0` だった。コードは 1 行も
変えていない。時間を測るテスト（「全マップの最近傍計算が 1 サンプル 5 ms 未満」）が、ブラウザの
コールドスタートで落ちた疑いが濃厚。**時々落ちるテストは、いずれ誰にも読まれなくなる。**

**直し方**: 時間測定は合否ではなく計測値の報告に格下げするか、ウォームアップを 1 回挟んだうえで
閾値を 20 ms に緩める。

### G-2 【中】ビルドが途中で落ちると、タスクが消えた状態のデータが残る

`build_tasks()` と `build_landmarks()` は、書き出す前に `out_dir.glob("*.json")` を**先に全部 unlink** する。
取得や整形で例外が出ると、消えただけの `data/` が残る。そのままコミットすると
「タスクが 1 件も無い」版が公開される。

**直し方**: 一時ディレクトリに書き出し、最後にまとめて差し替える。

### G-3 【低】データの「意味」を見るテストが薄い

校正の幾何（POI が viewBox に収まるか等）は手厚い一方、内容の回帰が手薄。マップ数が減っていないか、
タスク数が急減していないか、`_any` が読めるか、タスク名が日本語か、量子化の clamp が起きていないか —
どれも上流の欠測で静かに壊れる箇所。

### G-4 【低】クローンした人は必ず 30 MB 取りに行くことになる

`tools/.cache/` は `.gitignore` 済みなので当然の挙動だが、README には「キャッシュがあれば使う」と
しか書いておらず、初回は必ず全取得になることが読み取れない。

## H. 文書とライセンス

### H-1 【中】README に「公開する（無料）」の節がまるごと 2 回入っている

400 行目以降、「公開する（無料）」から「訪問者から見た性質」までの約 80 行が完全に重複している。
「サンプル別の実測値」の見出しも 2 行連続で出ている。おそらく編集時の貼り付け事故。

**直し方**: 後半の重複ブロックを削除。`## 状態` の直後から 1 回ぶんだけ残す。

### H-2 【中】README の数字が実データとずれている

「268 タスク / 591 ゾーン / 419 候補地点」「全 11 ファイルで 234 KB」と書かれているが、実際は
**13 ファイルで 517 タスク（延べ 758 件）**、合計 575 KB。地点の 1,746 件は合っている。
`## 状態` の表（S7 一部・S8 進行中）も現状より控えめ。

**直し方**: 数値は `build_data.py` の出力から README に自動反映するか、README からは数値を落として
`mapdb.json` を唯一の出典にする。手で同期すると必ずまたずれる。

### H-3 【低】素材ライセンスの禁止事項を、画面にも 1 行置く

地図素材（CC BY-NC-SA 4.0）は「ゲーム内レーダー / ESP オーバーレイでの利用」を明確に禁じている。
README には書いてあるが、PWA の単独ウィンドウは**そのままオーバーレイとして使える形**なので、
画面側にも一言あると、配布物としての筋が通る。

**直し方**: フッターの「非公式ファンツール」の行に「ゲーム画面に重ねての使用は禁止」を追記。
